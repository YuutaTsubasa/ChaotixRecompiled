STEP 00

先搞懂：Recompiled 和模擬器差在哪First: how a recompilation differs from an emulator

模擬器像同步口譯：遊戲每執行一條機器指令，模擬器當下才去看懂它、照做一次。看一條、做一條，一秒要做幾千萬次。

Recompiled 像事先把整本書翻好：在你玩之前，就把遊戲的機器碼一段一段翻成 C++ 程式碼，再交給電腦自己的編譯器編成原生程式。玩的時候不用再「看懂」，直接執行翻好的版本。

但遊戲不只是程式，還有畫面晶片、音效晶片、計時器、中斷。這些硬體行為沒辦法「翻譯」，必須另外寫一層程式把它們重現出來。所以一個 Recompiled 移植其實是兩半：翻好的遊戲程式，加上一層硬體相容層。

An emulator is like a live interpreter: each time the game runs a machine instruction, the emulator reads it and carries it out, one at a time, tens of millions of times a second.

A recompilation is like translating the whole book in advance: before you play, the game's machine code is translated piece by piece into C++, which your computer's own compiler turns into a native program. While you play, nothing has to be read and understood again.

But a game is more than code. It talks to a video chip, sound chips, timers and interrupts. That hardware behaviour can't be translated; it has to be reproduced by a separate layer. So a recompiled port is two halves: the translated game code, and a hardware compatibility layer.

STEP 01

劃清法律界線，再寫第一行程式Draw the legal line before the first line of code

Recompiled 專案能公開，前提是不散布任何遊戲本身的東西。這一步要在一開始就定好，因為它會決定之後所有工具怎麼設計。

  • 玩家自己提供合法取得的 ROM。程式會先檢查 SHA-1（這裡是 0c2fff7b…7ced7），不符就不使用翻好的程式碼。
  • ROM、從 ROM 翻出來的程式碼（generated/）、截圖，全部列在 .gitignore，永遠不進 git，也不上傳任何雲端。
  • CI（GitHub 上的自動測試）拿不到遊戲檔，所以 CI 只測不需要遊戲的部分，例如指令語意、各個元件；需要遊戲的測試在開發者自己的電腦上跑。
  • 不需要 32X 的 BIOS：開機過程用程式重現（HLE），使用者不必另找 BIOS 檔。

A recompilation can be public only if it ships nothing from the game itself. Decide this on day one, because it shapes how every tool is designed.

  • Players supply their own legally obtained ROM. The program checks its SHA-1 (here 0c2fff7b…7ced7) and won't use the translated code with anything else.
  • The ROM, the code generated from it (generated/) and screenshots are all in .gitignore. They never go into git or any cloud service.
  • CI (the automatic tests on GitHub) never has the game, so it tests what doesn't need it: instruction semantics, individual components. Tests that need the game run on the developer's own machine.
  • No 32X BIOS is needed: the boot sequence is reproduced in code (HLE), so players don't have to find a BIOS file.
✓ 怎麼確認：CI 有一項叫「No game data」的檢查，專門確保 repo 裡沒有遊戲資料；另外任何超過 512 KB 的檔案都會被擋下。How you know: CI has a "No game data" job that checks the repo holds no game data, and it rejects any tracked file over 512 KB.

STEP 03

先寫「標準答案」：參考直譯器Write the answer key first: a reference interpreter

聽起來繞遠路，但這是整個專案最重要的決定：在寫翻譯器之前，先寫一個一條一條執行指令的直譯器（也就是一個小模擬器）。68000、SH-2、Z80 各一個。

它慢沒關係，它的工作是當標準答案。之後翻好的程式碼跑出來的結果，每一格都要跟它一模一樣。

關鍵技巧：每條指令「做什麼」只寫一次，寫在共用的語意檔（m68k_ops.h、sh2_ops.h）裡。直譯器用它，翻譯出來的 C++ 也呼叫同一份。這樣兩邊不會各自寫錯成不同的樣子。

It sounds like a detour, but it's the most important decision in the project: before writing the translator, write an interpreter that runs instructions one at a time (a small emulator). One each for the 68000, the SH-2 and the Z80.

It can be slow. Its job is to be the answer key: later, the translated code has to produce exactly the same result, every frame.

The key trick: what each instruction does is written once, in shared semantics headers (m68k_ops.h, sh2_ops.h). The interpreter uses them, and the generated C++ calls the very same code, so the two can't drift apart.

✓ 怎麼確認：拿處理器手冊上已知答案的例子寫單元測試，例如旗標、BCD、乘除法、SH-2 的 delay slot 順序。專案一開始就有 33 項這種測試。How you know: unit tests built from known answers in the CPU manuals: flags, BCD, multiply and divide, the SH-2 delay-slot order. The project started with 33 of them.

STEP 04

找出 ROM 裡哪些是程式：ROM 分析器Find which bytes are code: the ROM analyzer

ROM 是一大串數字，裡面混著程式、圖、聲音、文字。翻譯器只能翻程式，所以要先畫出地圖：

  • 從已知的入口（開機位址、中斷向量）開始，沿著每個跳躍、呼叫往下走，標出所有走得到的程式（控制流程圖、函式表）。
  • 遇到「跳到表格裡某個位址」的間接跳躍時，要解析那張表。
  • 有些入口靜態看不出來，就實際玩一遍，記錄執行過的位址（coverage 檔，只存位址，不含 ROM 內容），再回饋給分析器。

A ROM is a long run of numbers mixing code, graphics, sound and text. The translator can only translate code, so first you draw a map:

  • Start from the known entry points (the reset address, interrupt vectors), follow every jump and call, and mark all reachable code (a control-flow graph, a function list).
  • When a jump goes through a table of addresses, decode the table.
  • Some entry points can't be found statically, so play the game and record which addresses run (a coverage file holding only addresses, no ROM content), then feed that back to the analyzer.
✓ 怎麼確認：用「沒拿來產生 coverage 的另一段遊玩」去跑，看有多少程式是翻好的版本在執行。這個專案：68000 有 99.7–100%、SH-2 有 100% 的程式區塊直接跑翻好的原生碼。How you know: play a stretch that wasn't used to make the coverage, and count how much runs as translated code. Here, 99.7–100% of 68000 blocks and 100% of SH-2 blocks run as native code.

STEP 05

真正的翻譯：重編譯器The translation itself: the recompiler

重編譯器把地圖上的每個程式區塊，翻成一段 C++。翻出來的程式碼每行都附上原本的組合語言當註解，可以直接下中斷點除錯。

為什麼翻成 C++ 而不是更底層的 LLVM IR？因為 C++ 在每個平台都有現成的編譯器（MSVC、GCC、Clang、Android NDK、Xcode），翻一次就能到處編。

The recompiler turns each block on the map into a piece of C++. Every generated line carries the original assembly as a comment, and you can set breakpoints in it.

Why C++ and not lower-level LLVM IR? Every platform already has a C++ compiler (MSVC, GCC, Clang, the Android NDK, Xcode), so one translation builds everywhere.

STEP 06

補上硬體：相容層與時間Fill in the hardware: the compatibility layer and timing

翻好的程式會去讀寫硬體暫存器，這些要由相容層接住：兩組畫面晶片（逐條掃描線合成）、DMA、計時器、除法器、COMM 暫存器、FM／PSG／PWM 音源，以及開機流程。

最需要想清楚的是時間。四顆處理器在真機上是同時跑的，程式裡只能輪流跑。這個專案把每條掃描線切成 4 段固定時間片，每段依序跑 68000 → Z80 → 主 SH-2 → 副 SH-2。整個模型是確定性的：同樣的輸入，永遠得到同樣的結果，不受電腦快慢影響。

The translated code reads and writes hardware registers, and the compatibility layer answers: both video chips (composited line by line), DMA, timers, the divider, the COMM registers, the FM/PSG/PWM sound, and the boot sequence.

The part that needs the most thought is time. On the real console the four processors run at once; in a program they take turns. This project cuts each scanline into 4 fixed slices and runs 68000 → Z80 → master SH-2 → slave SH-2 in each. The whole model is deterministic: the same input always gives the same result, however fast the computer is.

! 真實的坑（issue #50）：遊戲自己的 SOUND TEST 沒有聲音。原因是 68000 暫停 Z80 時，Z80 沒有剛好跑到被暫停的那一刻。修法是先把 Z80 補跑到 68000 當下的時間，再改變它的狀態，跟真機一樣。A real trap (issue #50): the game's own SOUND TEST was silent. When the 68000 paused the Z80, the Z80 hadn't run up to that exact moment. The fix runs the Z80 up to the 68000's current time before changing its state, as the hardware does.

STEP 07

對答案：逐格 lockstep 驗證Check against the key: frame-by-frame lockstep

這一步回答「你怎麼知道翻譯沒翻錯？」。做法是讓兩台機器同時跑同一段遊戲：一台用翻好的原生程式，一台用第 3 步的直譯器。每一格結束時比較兩邊的所有東西：每顆 CPU 的暫存器、cycle 數、全部 RAM、顯示記憶體、32X 畫面緩衝、輸出的畫面。只要有一個 byte 不同，測試就失敗，並指出是哪一格、哪裡不同。

This step answers "how do you know the translation is right?". Run two machines on the same play session: one on the native translated code, one on the step-03 interpreter. At the end of every frame, compare everything: each CPU's registers and cycle counts, all of RAM, video memory, the 32X frame buffer, the output picture. If a single byte differs, the test fails and says which frame and where.

STEP 08

做成能玩的程式：前端Make it playable: the frontend

前端用 SDL3 處理視窗、全螢幕、畫面縮放、鍵盤／手把／觸控、聲音輸出和設定檔。還有一個沒有畫面的版本（chaotix_headless），專門給測試和量測用：可以照腳本按鍵、存截圖、輸出 WAV、印出每個 CPU 花了多少時間。

一個好習慣：聲音和畫面依模擬時間產生，不讓電腦的音效裝置反過來決定遊戲速度。

The frontend uses SDL3 for the window, fullscreen, scaling, keyboard/gamepad/touch, sound output and settings. There's also a windowless build, chaotix_headless, made for tests and measurement: it presses buttons from a script, saves screenshots, writes WAV files and reports how long each CPU took.

A good habit: produce sound and pictures from emulated time, and never let the computer's audio device decide how fast the game runs.

STEP 09

讓它比原版更好，但不破壞原版Improve on the original without breaking it

移植的價值常在「原版做不到的事」。這個專案加了真正的寬螢幕、時間挑戰、成就、作弊碼、存檔／讀檔、倒帶、網路連線、角色與音樂 mod 等等。原則是：不准偷偷改壞原本的遊戲。

以寬螢幕為例：不是把 4:3 畫面拉寬，而是讓遊戲自己的關卡繪圖程式多畫兩側的地形、物件和角色。並且有一項測試保證中間那 320 像素跟原版一模一樣。

A port earns its keep with things the original can't do. This one added real widescreen, time attack, achievements, cheats, save states, rewind, netplay, character and music mods and more. The rule: never quietly break the original game.

Take widescreen: the 4:3 picture isn't stretched; the game's own level renderer is extended to draw real tiles, objects and sprites at the sides. A test guarantees the centre 320 pixels stay identical to the original.

另一個例子：時間挑戰模式沒有自己發明選關畫面，而是找到遊戲裡原本就有、但正式版沒開放的 STAGE SELECT，照它的程式碼呼叫「開始關卡」，所以進關卡的方式跟遊戲本身完全相同。

Another example: time attack doesn't invent its own level picker. It uses a STAGE SELECT that is in the game but never reachable in the shipped version, calling its own "start level" routine, so a level starts exactly as the game itself would start it.

STEP 11

跑得更快：先量，再改，再證明Make it faster: measure, change, prove

有玩家說在慢手機上跑不順（issue #62）。目標定為：在同一台手機上比 PicoDrive 模擬器快，而且不能犧牲準確度，不准用跳格之類的偷吃步。

做法每次都一樣：在實體手機上用 headless 版量 3,000 格，找出最花時間的部分，改它，再用 lockstep 證明行為沒變，最後再量一次。

A player said it stuttered on slow phones (issue #62). The goal: be faster than the PicoDrive emulator on the same phone, without giving up accuracy; no frame-skipping shortcuts.

The method was the same every time: measure 3,000 frames with the headless build on the real phone, find the biggest cost, change it, prove with lockstep that behaviour didn't change, then measure again.

其中一次加速的故事：關卡中，遊戲每格大約 370 次把資料寫在 SH-2 程式碼的旁邊。原本每次寫入都讓「所有」翻好的函式重新檢查自己有沒有被改，3,000 格裡檢查了 4,049,824 次。改成每個函式只在自己的 byte 真的被改變時才重新檢查之後，同樣 3,000 格只剩 75 次。

One speed-up in detail: in a level the game writes about 370 times a frame right next to some SH-2 code. Each write used to make every translated function re-check itself: 4,049,824 checks in 3,000 frames. After each function was made to re-check only when its own bytes actually changed, the same 3,000 frames needed 75.

STEP 12

接玩家回報：先重現，再修，再用同一招驗證Handle reports: reproduce, fix, verify the same way

這個流程是專案擁有者訂的規則，每一個 issue 都照走。下面是一個完整的真實例子，就發生在這份文件寫成的同一天。

This loop is a rule set by the project owner, and every issue goes through it. Here is a complete real case from the same day this page was written.

案例：「音樂好像少了一些 32X 聲道」Case: "the music missed some 32X audio channels"

  1. 先看證據：留言掛在一段實機錄影下。把影片的音訊抽出來，跟模擬輸出對齊比較。結果 PWM（32X 的取樣音源）四個音軌都有在播，沒有少。
  2. 找標準：自己的程式不能當自己的標準。下載 PicoDrive 的 PC 版核心，寫一個小程式讓它不開視窗，跑同一個 ROM、按同樣的鍵、進同一關，把聲音和畫面存下來。
  3. 逐格比對：Mighty 的跑、跳、滾球、spin dash，兩邊逐格相同，所以「Mighty 動畫」不需要改。聲音方面，PicoDrive 的大鼓明顯比較響。
  4. 讀原始碼確認：讀 PicoDrive 的音源程式碼（只讀，不複製），確定每種音源的最大音量：FM ±8191、PSG ±2304、PWM ±32768，最後整體乘 0.875。跟實測的差距吻合。
  5. 修：照這些比例改混音；另外發現 PSG 雜訊聲道只有一半大，一起修正。
  6. 用同樣方法驗證：標題音樂 -23.3 dB 對 PicoDrive -23.5 dB（原本 -31.2），關卡 -20.2 對 -20.1，大鼓頻段從差 9.4 dB 變成 1 dB 以內。
  7. 修好之後又發現新問題：音量變大後，關掉音樂時的「啵」一聲也變大了。追查成因（PWM 停在非中點、波形被瞬間切斷），改成音量在 38 毫秒內漸變，並加一個測試：沒有漸變就會失敗。
  8. 發版：0.15.12，六個平台、全部測試、33 組逐格比對、Mac、實體手機都通過才發。
  1. Look at the evidence: the comment was under a gameplay video. Extract its audio and line it up with the emulated output. All four PWM tracks (the 32X's sample channel) were playing: nothing was missing.
  2. Find a reference: a program can't be its own yardstick. Download PicoDrive's PC core and write a small windowless host that runs the same ROM, presses the same buttons, enters the same level and saves the sound and frames.
  3. Compare frame by frame: Mighty's running, jumping, rolling and spin dash were identical frame for frame, so the "Mighty animation" needed no change. In the sound, PicoDrive's bass drum was clearly louder.
  4. Confirm in the source: read PicoDrive's sound code (read only, nothing copied) for each source's peak level: FM ±8191, PSG ±2304, PWM ±32768, the sum times 0.875. That matched the measured gap.
  5. Fix: mix at those levels; the PSG noise channel turned out to be half as loud as it should be, and was fixed too.
  6. Verify the same way: title music -23.3 dB vs PicoDrive -23.5 (was -31.2), level -20.2 vs -20.1, and the bass-drum band from 9.4 dB short to within 1 dB.
  7. The fix exposed another problem: with the louder mix, muting the music popped louder. Trace the cause (PWM parked off-centre, the waveform cut in one sample), ease volume changes over 38 ms, and add a test that fails without the easing.
  8. Release: 0.15.12, only after six platforms, every test, 33 lockstep runs, the Mac and the real phone all passed.
? 注意第 7 點：修完一個問題，不是交差，而是再量一次、再聽一次。「做到真的對」和「做到看起來能動」的差別，就在這裡。Note point 7: fixing one thing isn't the finish line; measure and listen again. That's the difference between "really right" and "seems to work".
